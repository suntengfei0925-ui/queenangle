# 购卡充值合并流程 PRD

## 1. 背景

当前系统中，会员余额充值和次卡购买是两套页面与两套入口。余额充值页负责选择充值档位、增加会员余额并更新折扣；次卡购买页负责选择次卡类型、增加会员次卡次数并记录实收金额。

真实门店操作中，老板通常先进入会员资料，再围绕这个会员完成充值、购卡、消费等动作。次卡购买不应再作为独立入口存在，而应合并到会员充值页中，形成统一的“购卡/充值”流程。

## 2. 目标

本次需求将“次卡购买”合并到现有会员充值页面。

目标包括：

- 页面支持余额充值和次卡购买两种模式。
- 余额充值档位为单选。
- 次卡为多选，但同一种次卡本次只能选一次。
- 余额充值和次卡购买互斥，一次提交只能做其中一种。
- 次卡购买金额按配置价格自动合计，不允许手动修改。
- 次卡购买可一次购买多种不同次卡，并生成一条业务记录。
- 作废时整单作废，统一回滚所有次卡次数。
- 删除独立次卡购买页面及旧的单卡购卡路径，不兼容旧历史记录。

本次不处理：

- 页面最终命名拍板。
- 次卡购买折扣、议价或手动改价。
- 同一种次卡一次购买多份。
- 余额充值和次卡购买同单叠加。
- 历史数据兼容迁移。

## 3. 使用角色与可见性

主要操作者为老板。

该页面可能在顾客付款时被顾客看到，因此页面应清晰展示本次选择、应收金额和支付方式。

会员余额、会员折扣、次卡剩余次数属于敏感经营数据，仍必须由云函数统一修改，不允许前端直接改写。

## 4. 使用流程

老板进入会员资料页，点击充值入口，进入“购卡/充值”页面。

页面顶部展示会员信息：

```text
会员姓名
手机号
当前余额
当前折扣
次卡总次数
```

页面展示两个业务选择区：

```text
充值档位
次卡充值
```

老板如果选择充值档位，则本次为余额充值；已选次卡自动清空。

老板如果选择次卡，则本次为次卡购买；已选充值档位自动清空。

次卡可以同时选择多种不同卡，每张卡只允许选一次。选中后高亮，再次点击取消。

老板选择支付方式后，页面显示对应收款二维码。

点击“完成充值”后，系统生成一条记录并更新会员状态。

## 5. 页面需求

### 5.1 页面命名

页面暂定名称：

```text
购卡/充值
```

最终命名后续由老板统一拍板。

提交按钮文案：

```text
完成充值
```

### 5.2 页面结构

页面建议结构：

```text
会员信息
充值档位
次卡充值
支付方式
本次汇总
备注
完成充值
```

### 5.3 充值档位

充值档位沿用当前逻辑：

- 单选。
- 展示充值金额和充值后折扣。
- 选择充值档位后，自动清空已选次卡。
- 余额充值会增加会员余额，并更新会员当前折扣。

展示示例：

```text
充 ¥1000.00
享 7.7折
```

### 5.4 次卡充值

次卡充值展示当前所有启用的次卡类型。

每张次卡展示：

```text
次卡名称
默认次数
价格
```

示例：

```text
手部护理10次卡
10 次 / ¥398.00
```

交互规则：

- 次卡支持多选。
- 同一种次卡本次只能选一次。
- 选中后高亮。
- 再次点击取消。
- 选择任意次卡后，自动清空已选充值档位。
- 不允许手动修改购买次数。
- 不允许手动修改单卡价格或合计金额。

### 5.5 支付方式与二维码

余额充值和次卡充值都必须选择支付方式。

支付方式沿用当前项目已有方式：

```text
微信
支付宝
现金
```

选择微信或支付宝后，继续显示对应收款二维码。

### 5.6 本次汇总

如果选择余额充值，汇总展示：

```text
余额增加
充值后折扣
实收金额
```

如果选择次卡充值，汇总展示：

```text
购买次卡明细
合计次数
实收金额
```

次卡汇总示例：

```text
手部护理10次卡    +10 次    ¥398.00
美睫5次卡         +5 次     ¥588.00
合计次数          15 次
实收金额          ¥986.00
```

### 5.7 备注

备注沿用当前充值页逻辑，为整次记录备注。

## 6. 业务规则

### 6.1 互斥规则

余额充值和次卡购买互斥。

```text
选择充值档位时，清空已选次卡。
选择次卡时，清空已选充值档位。
```

不采用提交时才报错的方式。

### 6.2 提交条件

提交时必须满足：

```text
已选择充值档位 或 已选择至少一张次卡
```

否则提示：

```text
请选择充值档位或次卡
```

同时必须选择支付方式，否则提示：

```text
请选择支付方式
```

### 6.3 余额充值规则

余额充值沿用当前逻辑：

- 增加会员余额。
- 更新会员当前折扣。
- 生成余额充值记录。
- 生成余额流水。
- 计入充值收入和今日实收。

### 6.4 次卡购买规则

次卡购买规则：

- 可一次购买多种不同次卡。
- 同一种次卡本次只能购买一次。
- 每张卡按配置的默认次数增加。
- 每张卡按配置价格计入本次实收。
- 总实收金额等于所有选中次卡价格之和。
- 不允许手动修改购买次数。
- 不允许手动修改实收金额。
- 不影响会员余额。
- 不影响会员当前折扣。
- 生成一条次卡购买记录。
- 每张卡生成对应次卡流水。
- 计入今日流水和次卡购买收入。

### 6.5 作废规则

余额充值作废沿用当前逻辑。

次卡购买作废为整单作废。

如果一次购买多张次卡，作废后所有本次购买的次卡次数都回滚。

不允许只作废其中某一张卡。

录错后应整单作废，再重新录入。

## 7. 记录与展示

### 7.1 记录类型

次卡购买建议继续使用或重构为统一的：

```text
card_purchase
```

但不再作为单卡记录设计，而是支持 `cardItems[]` 多卡明细。

项目仍处于开发阶段，可以删除旧的单卡购卡路径和旧历史兼容逻辑，避免叠加复杂度。

### 7.2 历史列表摘要

余额充值：

```text
充值后折扣：7.7折
```

单张次卡购买：

```text
购卡：手部护理10次卡
```

多张次卡购买：

```text
购卡：手部护理10次卡、美睫5次卡
```

### 7.3 记录详情

次卡购买详情需要展示每张卡：

```text
次卡名称
增加次数
单卡价格
```

示例：

```text
手部护理10次卡    +10 次    ¥398.00
美睫5次卡         +5 次     ¥588.00
```

同时展示：

```text
实收金额
支付方式
备注
记录状态
创建时间
```

### 7.4 快照规则

次卡购买记录必须保存购买时的快照：

```text
cardTypeId
cardName
purchaseTimes
priceCent
```

后续修改次卡名称、默认次数或价格，不影响历史记录展示。

## 8. 数据需求

### 8.1 members

继续使用：

```text
balanceCent
currentDiscount
currentDiscountLabel
cardBalances[]
```

余额充值更新余额和折扣。

次卡购买只更新 `cardBalances[]`。

### 8.2 records

余额充值继续使用现有充值记录结构。

次卡购买记录建议结构：

```text
type = card_purchase
memberId
memberName
cardItems[]
actualReceivedCent
paymentMethod
memberBefore
memberAfter
remark
status
occurredAt
businessDate
createdByOpenid
createdAt
updatedAt
```

`cardItems[]` 示例：

```json
[
  {
    "cardTypeId": "card_type_id_1",
    "cardName": "手部护理10次卡",
    "purchaseTimes": 10,
    "priceCent": 39800
  },
  {
    "cardTypeId": "card_type_id_2",
    "cardName": "美睫5次卡",
    "purchaseTimes": 5,
    "priceCent": 58800
  }
]
```

兼容字段如 `cardTypeId`、`cardName`、`purchaseTimes` 可删除或不再作为核心字段使用。

### 8.3 card_flows

每张购买的次卡生成一条流水：

```text
memberId
memberName
type = purchase
sourceRecordId
cardTypeId
cardName
deltaTimes
remainingTimes
remark
createdAt
```

### 8.4 balance_flows

次卡购买不生成余额流水。

余额充值继续生成余额流水。

## 9. 异常情况

- 未选择充值档位且未选择次卡：提示“请选择充值档位或次卡”。
- 未选择支付方式：提示“请选择支付方式”。
- 次卡类型已停用或不存在：禁止提交，提示“次卡类型不可用”。
- 重复提交：应避免重复生成记录。
- 云函数执行失败：不得出现记录生成但会员次数未更新，或次数更新但记录未生成。
- 作废时如会员次卡次数不足以回滚，应提示异常并阻止作废，避免出现负数次数。

## 10. 权限与隐私

本次不新增员工和老板权限区分，沿用当前 owner 校验。

会员余额、折扣、次卡次数必须通过云函数修改。

页面可能给顾客看，应明确展示本次实收金额和支付方式，但不需要展示内部流水字段。

## 11. 验收标准

1. 进入购卡/充值页，可以看到会员当前余额、当前折扣和次卡总次数。
2. 选择一个充值档位后，再选择次卡，充值档位被自动取消。
3. 选择一张次卡后，再选择充值档位，已选次卡被自动取消。
4. 一次选择两种不同次卡，页面高亮两张卡，并展示合计次数和合计金额。
5. 同一种次卡不能在同一单里重复购买多份。
6. 次卡购买提交后，会员对应次卡次数分别增加，余额和折扣不变。
7. 次卡购买记录在今日流水中出现，并计入次卡购买收入。
8. 多卡购买记录详情展示每张卡的名称、增加次数和单卡价格。
9. 作废多卡购买记录后，所有本次增加的次卡次数全部回滚。
10. 独立次卡购买页面和旧单卡购卡路径被清理，不再形成两套购卡流程。

## 12. 待确认问题

暂无影响本次开发的问题。

页面最终名称后续由老板统一确认。

### 建议拆分

- 第 1 步：重构 `card_purchase` 记录结构，支持 `cardItems[]` 多卡明细。
- 第 2 步：统一后端购卡逻辑，删除旧单卡购卡路径，避免两套接口长期并存。
- 第 3 步：改造会员充值页，增加次卡多选区、互斥选择逻辑和购卡汇总。
- 第 4 步：改造提交逻辑，根据选择调用余额充值或次卡购买。
- 第 5 步：改造会员详情、今日流水、记录详情展示。
- 第 6 步：改造作废重放逻辑，支持多卡 `card_purchase` 整单回滚。
- 第 7 步：删除独立 `card-purchase` 页面注册和无用代码。

### 测试场景

正常流程：

- 余额充值单选并提交成功。
- 单张次卡购买成功。
- 多张不同次卡购买成功。
- 选充值档位后再选次卡，充值档位自动取消。
- 选次卡后再选充值档位，次卡自动取消。
- 支付方式选择后展示对应二维码。

异常流程：

- 未选择充值档位或次卡时提交失败。
- 未选择支付方式时提交失败。
- 停用次卡不可被购买。
- 重复点击不会生成重复记录。

数据回归：

- 余额充值仍增加余额并更新折扣。
- 次卡购买只增加次卡次数，不影响余额和折扣。
- 次卡购买计入今日实收和次卡购买收入。
- 作废余额充值后余额和折扣正确回滚。
- 作废多卡购买后所有卡次数正确回滚。
- 记录详情使用购买时快照，不受后续次卡配置修改影响。
