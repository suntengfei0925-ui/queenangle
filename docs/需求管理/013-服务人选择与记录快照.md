# 服务人选择与记录快照 PRD

## 1. 背景

当前系统支持散客结账和会员结账，但消费记录只保存创建人 `createdByOpenid`，没有明确保存本次实际服务人员。

门店后续需要按服务人统计提成，因此散客消费、会员结账都必须记录“服务人”。服务人应来自当前可登录系统的白名单人员，并在记录提交时保存姓名快照，避免后续白名单改名影响历史账目。

## 2. 目标

在散客结账、会员结账页面增加“服务人”字段。

目标包括：

- 服务人默认当前登录白名单用户。
- 用户可手动更换为其他启用白名单人员。
- 服务人必填，因为后续提成统计需要依赖该字段。
- 提交消费记录时保存服务人的 `openid` 和 `name` 快照。
- 会员结账的客户确认与签字快照中包含服务人。
- 记录详情页展示服务人。

本次不处理：

- 多服务人分成。
- 项目级服务人。
- 提成计算。
- 提成统计报表。
- 充值、购卡、老会员补录等非消费记录的服务人。

## 3. 使用角色与可见性

主要操作者为白名单内可登录人员，例如老板或店内员工。

顾客可能在会员结账确认和签字时看到服务人姓名，因此服务人姓名应使用白名单中的 `name`，不展示 `openid`。

服务人名单只展示 `enabled !== false` 的白名单人员。已停用人员不出现在可选名单中。

## 4. 使用流程

### 4.1 散客结账

1. 操作者进入散客结账页。
2. 页面在“消费项目”上方显示服务人行，默认当前登录人。
3. 如需更换服务人，点击服务人姓名。
4. 系统打开自定义服务人选择面板。
5. 操作者点击目标服务人后，面板关闭，页面服务人更新。
6. 操作者正常选择消费项目、填写金额、选择支付方式并提交。
7. 系统创建散客消费记录，并保存服务人快照。

### 4.2 会员结账

1. 操作者进入会员结账页。
2. 页面在会员摘要下方、“消费项目”上方显示服务人行，默认当前登录人。
3. 如需更换服务人，点击服务人姓名并选择其他启用白名单人员。
4. 操作者选择普通项目、次卡或两者混合结账。
5. 点击完成结账后，会员确认弹窗展示本次服务人。
6. 客户确认并签字。
7. 如签字后更换服务人，原签字失效，需要重新确认并签字。
8. 最终提交成功后，系统创建会员结账记录，并保存服务人快照。

## 5. 页面需求

### 5.1 服务人展示行

在结账表单中增加一行轻量展示：

```text
服务人    张三 >
```

位置：

- 散客结账：放在“消费项目”上方。
- 会员结账：放在会员摘要下方、“消费项目”上方。

视觉要求：

- 整体保持小小的一行，不占用太多收银页面空间。
- 左侧为固定文案 `服务人`。
- 右侧为当前服务人姓名和进入提示。
- 姓名可点击，用于更换服务人。
- 不使用微信原生 `picker`。

### 5.2 服务人选择面板

点击服务人姓名后，打开自定义服务人选择面板。推荐使用底部小弹层或轻量弹窗。

面板内容：

```text
选择服务人
张三
李四
王五
```

交互要求：

- 列表展示启用白名单人员姓名。
- 当前选中人员高亮或显示选中标记。
- 点击某个人后立即切换并关闭面板。
- 点击取消或遮罩关闭时，保留原服务人。
- 停用人员不展示。

### 5.3 会员确认弹窗

会员结账已有客户确认和签字流程。本次确认弹窗中需要展示服务人：

```text
服务人：张三
```

服务人可以作为小行信息展示，不需要比金额、余额、次卡变化更突出。

### 5.4 记录详情页

记录详情页需要展示服务人：

```text
服务人：张三
```

今日流水列表和会员历史列表本期可以不展示服务人，避免列表信息过密。

## 6. 业务规则

### 6.1 适用范围

本需求只适用于：

- `guest_consumption`
- `member_checkout`
- 兼容历史接口名时的 `member_consumption`

会员结账中的以下场景都必须有服务人：

- 纯普通项目结账。
- 纯次卡结账。
- 普通项目 + 次卡混合结账。

### 6.2 单订单单服务人

一笔订单只允许一个服务人。

如果现实业务中有两位服务人，本期不做项目级拆分或多人分成。实际使用时可以分两次记账。

### 6.3 默认服务人

每次打开散客结账或会员结账页时，默认服务人都是当前登录人。

手动更换服务人只影响当前这笔待提交订单，不影响当前登录人，也不影响下一笔订单默认值。

系统不记住上一笔手动选择过的服务人。

### 6.4 必填规则

服务人为必填。

正常情况下由当前登录人自动填充。如果服务人信息缺失，禁止提交，并提示：

```text
服务人信息加载失败，请重试
```

### 6.5 白名单规则

默认服务人和可选服务人均来自 `owner_whitelist`。

服务人名单只包含 `enabled !== false` 的人员。

如果被选中的服务人在提交前被停用，后端应拒绝提交，并提示重新选择服务人。

### 6.6 历史快照

记录提交时保存 `servicePersonName` 快照。

白名单人员后续改名后，历史记录保持当时保存的 `servicePersonName`，新订单使用新名字。

### 6.7 作废规则

作废记录时，服务人字段保留。

服务人字段不参与会员余额、折扣、次卡次数回滚。

未来提成统计应只统计有效记录，不统计作废记录。

## 7. 缓存规则

当前登录人的服务人信息不应在结账页现场查询，否则会影响收银速度。

建议规则：

- 登录校验时返回当前白名单用户的 `openid` 和 `name`。
- 前端将当前用户信息缓存到全局状态或本地缓存。
- 小程序启动、登录成功或进入结账相关页面时，静默刷新启用白名单人员列表。
- 结账页优先使用已缓存的当前用户和服务人名单。
- 如果服务人名单缓存暂时没有加载完成，但当前登录用户信息已存在，则页面可以先只显示当前登录人为服务人，后台刷新后再补全可选名单。

服务人名单加载失败时：

- 不影响默认当前服务人。
- 点击更换服务人时，可提示名单加载失败。
- 如果当前服务人也缺失，则禁止提交。

## 8. 数据需求

### 8.1 owner_whitelist

沿用现有集合：

```text
openid
name
enabled
createdAt
```

登录接口需要能返回当前白名单用户的 `name`。

### 8.2 records

消费记录新增字段：

```text
servicePersonOpenid
servicePersonName
```

字段说明：

- `servicePersonOpenid`：本次服务人的白名单 `openid`。
- `servicePersonName`：提交时白名单中的姓名快照。

### 8.3 signatureSnapshot

会员结账签字快照需要增加：

```text
servicePersonOpenid
servicePersonName
```

签字快照中的服务人必须与最终保存记录中的服务人一致。

## 9. 签字有效性

会员结账签名绑定的是当时那一版确认内容。

服务人属于客户确认内容的一部分，因此签字后如果更换服务人，原签名失效，必须重新确认并签字。

签名失效规则应增加服务人字段：

- 服务人发生变化时，签名失效。
- 重新确认弹窗中展示新的服务人。
- 客户重新签字后，才能最终提交。

## 10. 权限与隐私

当前用户不在白名单时，沿用现有逻辑，不能进入系统。

服务人姓名可能被顾客看到，但只展示白名单中的业务姓名，不展示 `openid`。

记录详情页展示服务人，便于记账和后续追溯。

## 11. 异常情况

- 当前用户不在白名单：沿用现有逻辑，不能进入系统。
- 当前用户白名单缺少 `name`：不能提交消费记录，提示服务人信息加载失败。
- 服务人名单加载失败：不影响默认当前服务人；点击更换时提示名单加载失败。
- 被选中的服务人在提交前被停用：后端拒绝提交，并提示重新选择服务人。
- 签字后更换服务人：签字失效，需要重新确认并签字。
- 记录作废：服务人快照保留，不参与会员状态回滚。

## 12. 验收标准

1. 打开散客结账页，服务人默认显示当前登录人的白名单姓名。
2. 打开会员结账页，服务人默认显示当前登录人的白名单姓名。
3. 点击服务人姓名，可以从启用白名单人员中切换服务人。
4. 停用白名单人员不出现在服务人选择列表中。
5. 散客结账提交后，记录保存 `servicePersonOpenid` 和 `servicePersonName`。
6. 会员普通项目结账、纯次卡结账、混合结账都必须保存服务人。
7. 会员结账确认弹窗展示服务人。
8. 会员结账签字快照包含服务人。
9. 签字后更换服务人，原签字失效并要求重新签字。
10. 记录详情页展示服务人姓名。
11. 白名单人员改名后，历史记录仍展示当时保存的服务人姓名快照，新记录使用新名字。
12. 作废记录后，记录详情仍保留服务人信息。

- 默认当前登录人。
- 自定义服务人选择面板，不使用原生 picker。
- 服务人必填。
- 保存 `openid + name` 快照。
- 会员签字快照包含服务人。

### 建议拆分

- 第 1 步：登录接口返回当前白名单用户 `name`，前端缓存当前用户信息。
- 第 2 步：增加启用白名单人员列表读取接口，并做本地或全局缓存。
- 第 3 步：封装轻量服务人选择组件或页面内复用逻辑。
- 第 4 步：改造散客结账页，展示、切换、提交服务人。
- 第 5 步：改造会员结账页，展示、切换、纳入签字快照和签字失效判断。
- 第 6 步：后端创建记录时校验服务人仍为启用白名单人员，并保存快照。
- 第 7 步：记录详情页展示服务人。

### 测试场景

正常流程：

- 当前登录人为张三，打开散客结账页默认显示张三，提交后记录保存张三。
- 当前登录人为张三，打开会员结账页默认显示张三，提交后记录保存张三。
- 手动切换为李四后提交，记录保存李四，不保存张三。
- 会员纯次卡结账也要求并保存服务人。
- 会员普通项目结账和混合结账都保存服务人。
- 记录详情页能看到服务人。

异常流程：

- 服务人名单加载失败，但当前登录人已缓存时，仍可用当前登录人提交。
- 当前登录人缺少白名单 `name` 时，禁止提交并提示服务人信息加载失败。
- 停用人员不出现在选择列表中。
- 被选中的服务人提交前被停用，后端拒绝提交。
- 会员签字后更换服务人，页面要求重新签字。

数据回归：

- 记录保存后包含 `servicePersonOpenid` 和 `servicePersonName`。
- 会员签字快照包含服务人字段。
- 白名单李四改名后，旧记录仍展示旧快照，新记录展示新名字。
- 作废记录后服务人字段保留。
- 现有充值、购卡、老会员补录流程不受影响。
