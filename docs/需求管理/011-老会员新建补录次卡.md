# 老会员新建补录次卡 PRD

## 1. 背景

当前“新建会员补录”已支持补录老会员的初始余额、初始折扣、线下本子和页码，但遗漏了老会员线下已有次卡的剩余次数。

上线初期，很多会员已经在线下购买并使用过次卡。系统迁移时需要把这些剩余权益一起录入，否则会员资料不完整，后续结账核销也不准确。

本需求是在现有“老会员新建补录”能力上补充“初始次卡”迁移能力，只处理新建会员时的一次性补录，不开放已有会员的前台修改入口。

## 2. 目标

- 在新建会员页面的“补录老会员信息”区域增加“初始次卡”补录能力。
- 支持从系统已有次卡类型中选择多种次卡，并录入各自剩余次数。
- 次卡补录只表示历史权益迁移，不计入购卡收入、今日实收或充值统计。
- 补录后的次卡进入会员当前次卡余额，后续可在会员结账中正常核销。
- 补录后前台不可修改初始次卡，如录错只能通过后台修正。

本次不调整次卡项目配置能力，不调整购卡/充值流程，不新增员工权限体系。

## 3. 使用角色与可见性

当前仍只考虑老板使用，沿用现有老板白名单权限。

会员详情页展示当前次卡剩余次数，但不需要标注该次卡是否来自补录。补录来源和补录明细主要在历史记录详情中查看。

客户一般不直接操作该页面，但现实场景中老板可能和客户一起看手机，因此确认弹窗中的次卡信息需要清晰、准确，避免把老会员权益录错。

## 4. 使用流程

老板进入新建会员页面，填写会员姓名、手机号、生日等基础信息。

老板点击“补录老会员信息”展开补录区域。补录区域保留现有初始余额、初始折扣、来源本子和页码，并新增“初始次卡”模块。

“初始次卡”模块列出当前启用的所有次卡类型。老板点击某张次卡后，该次卡高亮，并在卡片内出现“剩余次数”输入框。再次点击该次卡时取消选中，并清空该次卡输入值。

老板可以同时选择多种次卡。保存时，如果填写了余额、折扣、本子页码或任意初始次卡，都判定为“补录导入”，并弹出二次确认。确认弹窗必须展示初始次卡明细。

确认后，系统一次性创建会员、写入老会员补录记录、写入余额流水、写入次卡流水，并更新会员当前余额、折扣和次卡余额。任一步失败都应整体失败。

## 5. 页面需求

### 5.1 入口与位置

“初始次卡”只在新建会员时出现，编辑已有会员时不出现。

入口沿用现有“补录老会员信息”展开区，不新增独立页面。位置放在初始余额、初始折扣、来源本子和页码之后。

### 5.2 次卡选择

页面列出当前启用的所有次卡类型。

次卡类型来源于系统次卡配置。若线下本子里存在某种次卡，但系统里尚未配置或已停用，应先到次卡设置里新增或启用，再回到新建会员补录。

每种次卡在补录区只出现一次。即使客户线下买过多张同类卡，也在同一项里填写汇总剩余次数。

示例：

```text
手部护理10次卡：剩余 13 次
```

### 5.3 交互规则

- 点击次卡：选中并高亮。
- 选中后：在该次卡卡片内显示“剩余次数”输入框。
- 再次点击已选次卡：取消选中并清空剩余次数。
- 未选中次卡：不展示该次卡的次数输入框。
- 多张次卡：允许同时选中多种不同次卡。

### 5.4 剩余次数输入

剩余次数必须是正整数。

不允许：

- 空值。
- `0`。
- 小数。
- 负数。

剩余次数允许超过该次卡类型配置的标准总次数。例如“10次卡”允许补录剩余 `13` 次，因为老会员可能在线下购买过多张同类卡，系统按同一 `cardTypeId` 汇总剩余次数。

## 6. 业务规则

### 6.1 补录导入判定

满足以下任意条件，都判定为“补录导入”：

- 填写非默认初始余额。
- 填写非默认初始折扣。
- 填写来源本子和页码。
- 选择任意初始次卡并填写剩余次数。

只补录次卡、不补余额、不补折扣、不填本子页码时，也算 `imported` 补录导入。

### 6.2 次卡补录性质

初始次卡表示历史权益迁移，不是当天卖卡。

因此：

- 不走 `card_purchase`。
- 不要求支付方式。
- 不生成购卡收入。
- 不计入今日实收。
- 不计入充值收入。
- 不计入购卡收入。
- 不计入消费金额。
- 不计入余额支付。

### 6.3 记录命名

现有 `member_initial_balance` 记录继续作为老会员补录主记录使用，但前端展示文案建议改为“老会员补录”。

原因是该记录以后可能只包含初始次卡，不一定包含初始余额。继续展示“初始余额”会造成理解偏差。

记录详情中应展示完整补录内容：

- 初始余额。
- 初始折扣。
- 来源本子和页码。
- 初始次卡明细。

### 6.4 创建后修改

初始次卡和初始余额、初始折扣一样敏感。会员创建后，前台不允许修改初始次卡。

如录入错误，暂时通过后台人工修正。

### 6.5 作废规则

老会员补录记录允许整条作废。作废后通过会员状态重放恢复余额、折扣和次卡状态。

作废该补录记录后，该记录写入的初始余额、初始折扣和初始次卡都应从会员当前状态中移除。

## 7. 数据需求

### 7.1 members

沿用现有会员字段：

```text
cardBalances[]
memberSource
offlineBook
offlinePage
importRemark
```

`cardBalances[]` 按 `cardTypeId` 汇总剩余次数。

示例：

```json
[
  {
    "cardTypeId": "card_type_id",
    "cardName": "手部护理10次卡",
    "remainingTimes": 13
  }
]
```

### 7.2 records

沿用现有 `member_initial_balance` 记录类型，增加 `cardItems[]`。

核心字段：

```text
type = member_initial_balance
status
memberId
memberName
amountCent
actualReceivedCent = 0
paymentMethod = ""
discount
discountLabel
offlineBook
offlinePage
cardItems[]
remark
memberBefore
memberAfter
occurredAt
businessDate
createdByOpenid
createdAt
updatedAt
```

`cardItems[]` 示例：

```json
[
  {
    "cardTypeId": "card_type_id",
    "cardName": "手部护理10次卡",
    "initialTimes": 13
  }
]
```

规则：

- `actualReceivedCent` 固定为 `0`。
- `paymentMethod` 固定为空。
- `cardItems[]` 只保存补录的初始次卡快照。
- `memberAfter.cardBalances[]` 应包含补录后的次卡余额。

### 7.3 card_flows

新增次卡流水类型：

```text
initial_card
```

每张补录次卡生成一条 `card_flows`。

字段：

```text
memberId
memberName
type = initial_card
sourceRecordId
cardTypeId
cardName
deltaTimes
remainingTimes
remark
createdAt
```

规则：

- `sourceRecordId` 指向本次 `member_initial_balance` 记录。
- `deltaTimes` 等于补录剩余次数。
- `remainingTimes` 等于写入后的剩余次数。
- `remark` 使用系统生成的老会员补录备注。

## 8. 展示需求

### 8.1 会员详情页

会员详情页的“次卡明细”展示当前剩余次数即可，不需要标注这张卡是否来自补录。

示例：

```text
手部护理10次卡    13 次
```

### 8.2 历史记录列表

`member_initial_balance` 的展示文案建议由“初始余额”改为“老会员补录”。

摘要建议展示关键信息：

```text
老会员补录：余额 ¥500.00 / 7.7折 / 次卡 2种
```

如果没有余额或折扣，只补录次卡，也应能展示：

```text
老会员补录：次卡 2种
```

### 8.3 记录详情页

记录详情页展示本次补录的完整快照：

- 初始余额。
- 初始折扣。
- 来源本子和页码。
- 初始次卡列表。

次卡列表展示：

```text
手部护理10次卡    初始 13 次
足部护理10次卡    初始 5 次
```

## 9. 异常情况

- 未展开补录区域且未填写任何补录字段：按普通新建会员处理。
- 选中次卡但未填写剩余次数：禁止保存，并提示“请填写已选次卡的剩余次数”。
- 剩余次数为 `0`：禁止保存。
- 剩余次数为小数：禁止保存。
- 剩余次数为负数：禁止保存。
- 剩余次数不是数字：禁止保存。
- 次卡类型不存在：禁止保存。
- 次卡类型已停用：禁止保存。
- 同一种次卡重复提交：后端应拒绝。
- 创建会员、写入记录、写入余额流水、写入次卡流水、更新会员任一步失败：整体失败，不写入半成品数据。
- 重复点击保存：应避免重复创建会员或重复补录次卡。

## 10. 权限与隐私

当前系统短期只有老板使用，沿用现有老板白名单校验。

初始次卡属于会员权益数据，敏感程度和初始余额、初始折扣一致。新建补录时允许填写，会员创建后前台不可修改。

二次确认弹窗必须展示初始次卡明细，避免老板误录后直接保存。

## 11. 验收标准

1. 新建会员不展开补录区域，保存后无初始次卡，会员来源为 `normal`。
2. 新建会员只选择一张次卡并填写剩余 `3` 次，保存前弹窗展示该次卡和次数。
3. 确认保存后，会员详情“次卡明细”展示该次卡剩余 `3` 次。
4. 一次选择多张次卡，保存后 `cardBalances[]` 中分别写入对应剩余次数。
5. 只补次卡时，会员来源为 `imported`，历史记录显示“老会员补录”。
6. 只补次卡时，不增加今日实收、充值收入或购卡收入。
7. 选中次卡但不填次数，保存失败。
8. 输入 `0` 次，保存失败。
9. 输入负数次数，保存失败。
10. 输入小数次数，保存失败。
11. 剩余次数超过次卡标准总次数时允许保存。
12. 作废该补录记录后，会员初始次卡被回放移除。
13. 补录成功后，会员结账页可以选择并核销该次卡。

## 12. 待确认问题

暂无。

已确认规则：

- 可补录多个次卡。
- 只列出当前启用的次卡类型。
- 选中后才出现剩余次数输入框。
- 剩余次数必须为正整数。
- 只补次卡也算补录导入。
- 不生成 `card_purchase`。
- 使用 `member_initial_balance` 作为补录主记录。
- 新增 `initial_card` 次卡流水。
- 前台不可修改初始次卡。

## 开发交接版

### 影响范围

- 页面：`miniprogram/pages/member-edit`。
- 页面：`miniprogram/pages/member-detail`。
- 页面：`miniprogram/pages/record-detail`。
- 工具：`miniprogram/utils/format.js`。
- 云函数：`cloudfunctions/business/index.js`。
- 数据集合：`members`、`records`、`card_flows`、`card_types`。
- 文档：`docs/data-model.md`、`docs/business-rules.md` 后续实现时应同步更新。

### 建议拆分

- 第 1 步：扩展新建会员补录数据结构，支持 `importInfo.cardItems[]`。
- 第 2 步：后端校验补录次卡，只允许启用次卡，剩余次数必须为正整数，同一种次卡不得重复。
- 第 3 步：改造 `saveMember` 创建会员事务，写入初始 `cardBalances[]`、`member_initial_balance.cardItems[]` 和 `initial_card` 次卡流水。
- 第 4 步：更新会员状态重放逻辑，让 `member_initial_balance.cardItems[]` 参与初始次卡回放。
- 第 5 步：改造新建会员补录区 UI，加载启用次卡，支持多选和剩余次数输入。
- 第 6 步：更新二次确认弹窗，展示补录次卡明细。
- 第 7 步：更新记录摘要、记录详情和格式化文案，将 `member_initial_balance` 展示为“老会员补录”。
- 第 8 步：回归统计，确认补录次卡不进入任何收入口径。

### 测试场景

- 普通新建会员，不填写补录字段。
- 只补初始余额和折扣。
- 只补一张初始次卡。
- 同时补录余额、折扣、本子页码和多张次卡。
- 补录次卡剩余次数大于标准总次数。
- 选中次卡但不填剩余次数。
- 输入 `0`、小数、负数、非数字次数。
- 后端收到重复 `cardTypeId`。
- 后端收到已停用或不存在的次卡类型。
- 补录成功后查看会员详情次卡明细。
- 补录成功后做一次会员结账并核销次卡。
- 作废补录记录后检查会员余额、折扣、次卡状态。
- 首页统计、今日流水、记录详情确认补录次卡不计入收入。
