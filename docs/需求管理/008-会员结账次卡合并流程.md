# 会员结账次卡合并流程 PRD

## 1. 背景

当前系统中，会员消费和次卡核销是两套业务能力。会员消费页负责普通项目结账、会员余额、折扣和补差价；次卡核销已有后端能力，但当前小程序已不再暴露独立入口。

真实门店场景中，老板更关注“客户一次到店发生了什么”，而不是拆成多条孤立业务动作。因此会员结账需要支持在同一次到店中同时记录：使用次卡、普通收费项目、余额支付、补差价和备注。

## 2. 目标

本次需求将现有会员消费流程升级为“会员结账”流程。

目标包括：

- 会员结账页展示该会员可用次卡。
- 老板可在同一页选择一张或多张次卡。
- 每张选中的次卡本次固定扣 1 次。
- 老板仍可继续选择普通服务项目并填写项目原价。
- 纯次卡结账允许提交。
- 一次到店只形成一条“会员结账”记录。
- 作废时整条会员结账记录整体作废，并回滚余额、折扣和次卡次数。
- 删除独立次卡核销页面及相关入口，不兼容旧历史 `card_use` 记录。

本次不处理：

- 销卡收入统计设计。
- 提交前二次确认弹窗。
- 次卡和具体服务项目的强绑定。
- 历史数据兼容迁移。

## 3. 使用角色与可见性

主要操作者为老板。

会员结账页面可能在客户面前操作，因此页面应避免展示复杂内部账务说明，但可以展示本次使用的次卡、普通项目、余额支付和补差价。

次卡余额、会员余额、折扣都属于敏感经营数据，只允许通过会员结账记录统一变更，不提供单独修改入口。

## 4. 使用流程

老板进入会员资料页，点击“消费结账”进入会员结账页。

页面顶部展示会员信息，包括姓名、手机号、当前余额、当前折扣。

如果该会员存在剩余次数大于 0 的次卡，则在“消费项目”模块上方展示“可用次卡”模块。

老板点击某张次卡后，该次卡绿色边框高亮；再次点击取消选中。可以同时选择多张次卡。

老板可以继续在下方选择普通服务项目，并为每个普通项目填写单项原价。普通项目流程沿用当前会员消费逻辑。

点击“完成结账”后，系统生成一条会员结账记录，并同时更新会员余额、折扣和次卡剩余次数。

## 5. 页面需求

### 5.1 页面命名

原“会员消费”页面调整为“会员结账”。

提交按钮文案为：

```text
完成结账
```

### 5.2 可用次卡模块

展示位置：会员信息下方、消费项目选择模块上方。

展示条件：

- 当前会员存在 `remainingTimes > 0` 的次卡时展示。
- 没有可用次卡时不展示该模块。

每张次卡展示：

```text
次卡名称
剩余 N 次
```

交互规则：

- 点击次卡后选中，高亮绿色边框。
- 再次点击取消选中。
- 可同时选中多张次卡。
- 每张选中次卡本次固定扣 1 次。
- 不显示“本次使用 1 次”。

### 5.3 普通项目模块

普通项目选择、项目原价输入、余额支付、补差价、支付方式选择，沿用当前会员消费页逻辑。

如果只选择次卡、不选择普通项目，则允许提交。

如果选择普通项目，则每个普通项目仍必须填写单项原价。

### 5.4 已选内容展示

已选内容中需要同时展示：

- 已选次卡：只显示次卡名称，不需要填写金额。
- 已选普通项目：显示项目名称和单项原价输入框。

次卡不绑定具体服务项目，不要求选择“美甲-纯色”之类的项目来解释次卡用途。

### 5.5 金额区展示

如果本次只有次卡，没有普通收费项目：

- 不展示整单原价、余额支付、补差价等金额计算区。
- 记录列表中展示为“使用次卡”。

如果本次包含普通收费项目：

- 展示现有金额计算区。
- 次卡部分不参与金额计算。

## 6. 业务规则

### 6.1 提交条件

会员结账至少需要选择一项内容：

```text
至少选 1 张次卡 或 至少选 1 个普通项目
```

不允许空提交。

### 6.2 次卡扣减

每张选中的次卡本次扣减 1 次。

扣减后不得小于 0。

买单页不展示剩余次数为 0 的次卡。

会员资料页继续展示 0 次次卡，方便知道客户曾经购买过。

### 6.3 普通项目金额计算

普通项目沿用当前会员消费逻辑：

```text
普通项目原价合计 = 所有普通项目单项原价之和
```

会员余额大于 0 且存在当前折扣时：

```text
消费金额 = 普通项目原价合计 * 当前折扣 / 10
余额支付 = min(当前余额, 消费金额)
补差价 = 消费金额 - 余额支付
```

余额为 0 时：

```text
消费金额 = 普通项目原价合计
余额支付 = 0
补差价 = 消费金额
```

余额扣到 0 后：

```text
currentDiscount = null
currentDiscountLabel = 无折扣
```

### 6.4 支付方式

纯次卡结账不需要选择支付方式。

如果普通项目产生补差价，则沿用当前逻辑，必须选择补差价支付方式。

### 6.5 统计口径

纯次卡记录需要出现在今日流水和会员历史记录中。

本次暂不设计“销卡收入”统计。

纯次卡记录暂不计入现有实收、消费金额、余额支付、充值、次卡购买收入等统计口径。

## 7. 记录与展示

### 7.1 记录类型

建议新增记录类型：

```text
member_checkout
```

原因：它可以表达纯次卡、纯普通项目、混合结账，比现有 `member_consumption` 更准确。

项目仍在开发阶段，历史记录可以删除，因此不需要兼容旧 `card_use` 记录。

### 7.2 历史列表摘要

会员详情历史记录、今日流水列表中，一次会员结账展示为一条记录。

纯次卡：

```text
使用次卡：手部护理10次卡
```

混合结账：

```text
次卡：手部护理10次卡；项目：美睫-单根
```

普通项目：

```text
项目：美甲-纯色、美睫-单根
```

如果一次使用多张次卡，列表中全部列出卡名，不做“等 N 张”省略。

### 7.3 记录详情

详情页需要展示完整内容。

次卡明细：

```text
手部护理10次卡    扣 1 次    剩余 7 次
```

普通项目明细：

```text
美睫-单根    原价 ¥128.00
```

金额明细仅在存在普通收费项目时展示：

```text
整单原价
当前折扣
消费金额
余额支付
补差价
补差价支付方式
```

纯次卡记录隐藏金额区。

### 7.4 快照规则

历史记录必须保存当时的次卡名称快照和普通项目名称快照。

后续修改次卡名称或服务项目名称，不影响历史记录展示。

## 8. 作废规则

会员结账记录只能整条作废。

作废后需要整体回滚：

- 会员余额
- 当前折扣
- 次卡剩余次数

不允许只作废其中某一张次卡或某一个普通项目。

作废后如需修正，应重新创建一条新的会员结账记录。

## 9. 数据需求

### 9.1 members

继续使用：

```text
cardBalances[]
balanceCent
currentDiscount
currentDiscountLabel
```

`cardBalances[]` 中保留 0 次次卡，会员资料页继续展示。

### 9.2 records

新增或调整会员结账记录字段：

```text
type = member_checkout
memberId
memberName
serviceItems[]
cardItems[]
originalAmountCent
consumptionAmountCent
balancePayCent
extraPayCent
actualReceivedCent
paymentMethod
extraPaymentMethod
discountApplied
discountLabelApplied
memberBefore
memberAfter
remark
status
occurredAt
businessDate
createdAt
updatedAt
```

`cardItems[]` 示例：

```json
[
  {
    "cardTypeId": "card_type_id",
    "cardName": "手部护理10次卡",
    "useTimes": 1,
    "remainingTimesAfter": 7
  }
]
```

### 9.3 card_flows

会员结账中使用次卡时，仍建议写入次卡流水，方便追溯：

```text
type = use
sourceRecordId = member_checkout recordId
deltaTimes = -1
remainingTimes
```

### 9.4 balance_flows

会员结账中发生余额支付时，沿用当前余额流水：

```text
type = consume
sourceRecordId = member_checkout recordId
amountCent = -balancePayCent
```

纯次卡不生成余额流水。

## 10. 异常情况

- 未选择次卡且未选择普通项目：提示“请选择次卡或服务项目”。
- 选择普通项目但未填写单项原价：沿用当前提示。
- 普通项目产生补差价但未选择支付方式：沿用当前提示。
- 次卡剩余次数不足：禁止提交，提示“次卡剩余次数不足”。
- 网络或云函数失败：不应部分扣减；会员状态和记录必须保持一致。
- 重复点击提交：应避免重复生成记录。

## 11. 权限与隐私

本次不新增员工和老板权限区分，沿用当前 owner 校验。

会员结账涉及余额、折扣和次卡次数变更，应继续只允许云函数修改最终会员状态，不允许前端直接写入会员余额或次卡次数。

本次不做提交前二次确认弹窗。二次确认属于后续单独需求。

## 12. 验收标准

1. 会员有 1 张剩余 3 次的次卡，进入会员结账页，页面显示该次卡；点击后绿色高亮，再次点击取消。
2. 只选择 1 张次卡并点击“完成结账”，提交成功，生成 1 条会员结账记录；会员该次卡剩余次数从 3 变为 2；余额和折扣不变。
3. 同时选择 1 张次卡和 1 个普通项目，普通项目按当前会员折扣和余额计算；提交后同一条记录中展示次卡明细和项目明细。
4. 会员某张次卡剩余 0 次时，会员资料页仍显示 0 次，但会员结账页不展示该次卡。
5. 作废一条混合会员结账记录后，余额、折扣和次卡次数全部回到提交前状态。
6. 今日流水中可以看到纯次卡会员结账记录，但金额统计不变化。

### 建议拆分

- 第 1 步：定义 `member_checkout` 数据结构，清理旧 `card_use` 新增入口逻辑。
- 第 2 步：改造会员结账页，增加可用次卡模块和已选次卡状态。
- 第 3 步：新增或改造云函数提交逻辑，一次事务内完成记录创建、余额扣减、次卡扣减、流水写入。
- 第 4 步：改造会员详情和记录详情展示，支持一条记录展示次卡明细和项目明细。
- 第 5 步：改造作废重放逻辑，支持 `member_checkout` 同时回滚余额、折扣和次卡次数。
- 第 6 步：清理 `card-use` 页面注册和无用代码。

### 测试场景

- 纯次卡结账成功。
- 普通项目结账仍保持现有逻辑。
- 次卡加普通项目混合结账成功。
- 多张次卡同时使用，每张扣 1 次。
- 0 次次卡不出现在买单页。
- 纯次卡不要求支付方式。
- 补差价场景仍要求支付方式。
- 作废纯次卡记录后次数恢复。
- 作废混合记录后余额、折扣、次卡次数全部恢复。
- 今日流水显示纯次卡记录，但金额统计不变化。
